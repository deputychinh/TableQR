# TQR-017: Tenant isolation and role e2e matrix

- Release: v0.5.0 · Status: review · Owner: Claude (deliver-loop)
- Spec: AC3 (tenant isolation), AC15 (roles); ADR 0003; docs/security.md (BOLA/BFLA rows)

## Story

As every restaurant on the platform, I want certainty that no other restaurant — and no staff member in the wrong role — can read or change my data, so that sharing one system is safe.

## Acceptance criteria

| Id  | Given                                                                                           | When                                             | Then                                                                                               |
| --- | ----------------------------------------------------------------------------------------------- | ------------------------------------------------ | -------------------------------------------------------------------------------------------------- |
| I1  | every staff endpoint in `test/support/role-matrix.ts`                                           | each of the 5 roles calls it                     | allowed roles pass, every other role gets 403 `FORBIDDEN`; no session → 401 (existing AC15 matrix) |
| I2  | a guarded route with no `@Roles`                                                                | any role calls it                                | 403 (deny by default)                                                                              |
| I3  | every matrix row that names a row of restaurant A (path id or body id) and is allowed to owners | the owner of restaurant B calls it with A's ids  | 404, and nothing changes                                                                           |
| I4  | the sweep                                                                                       | a new endpoint with an id is added to the matrix | it is swept automatically (no per-endpoint test to remember)                                       |

Guest-side isolation (a guest cookie of table/restaurant A reaching B) is covered per feature: `ordering.e2e-spec.ts` (phone of table A scanning table B), `guest-stream.e2e-spec.ts`, `billing.e2e-spec.ts`, `realtime.e2e-spec.ts` (streams of B never see A's events).

## Design

`test/roles.e2e-spec.ts`: an intruder owner signs up a second restaurant; `isolationCases` = matrix rows allowed to owners whose path or body references a fixture id (`/:…` in the path, `":":…` in the serialised body placeholders); each is called with the intruder's cookie and must answer 404 (streams: the opening status). The per-IP and per-user test limits are already raised in the e2e setup.

## Review round 1 fixes

- **"Nothing changes" is now proven, not just "404".** Each isolation call is wrapped in a snapshot of every row of the fixture restaurant (`test/support/tenant-snapshot.ts`: the `restaurants` row plus every table with a `restaurant_id` column, found in `information_schema`, so a new table is covered without editing a list); the snapshot after the call must equal the one before. Mutation check: `TablesService.update` changed to write by id first and check the tenant after (still answering 404) — the old status-only sweep passed, the new one fails on `PATCH /api/tables/:tableId` with the changed `seats` in the diff. Reverted.
- **One-shot rows get fresh fixtures**, one per role plus one for the intruder (so a missing tenant scope would really change a live row) plus one for the 401 sweep: payable bills and closable sessions (pools of 7, previously cycled 5 so the intruder hit an already-paid bill), held orders (confirm/reject), bookings that already started on their own free table (seat/cancel/no-show), free tables (open a session).
- **Route-coverage guard** (`› TQR-017 route coverage…`): `test/support/routes.ts` lists every route on the Express router after `app.init()`; `uncoveredRoutes` (in `role-matrix.ts`) fails on any route that is neither a `ROLE_MATRIX` row nor in `MATRIX_EXCLUSIONS` / `EXCLUDED_PREFIXES`, each with a reason (`/api/g/*` guest/public, sign-up/login/logout, health, the spec's own test-only route). Its first run listed 7 uncovered staff routes: `POST /api/sessions` (staff open — had no row at all), `POST /api/orders/:id/confirm|reject|flag-seen` and `POST /api/bookings/:id/seat|cancel|no-show`; all 7 are now matrix rows (so the role check and the isolation sweep cover them) rather than exclusions. Mutation check: deleting the `flag-seen` row makes the guard fail with `POST /api/orders/:/flag-seen`.
- Result: 59 matrix rows × 5 roles, 38 isolation rows each with the before/after snapshot, 332 tests in `roles.e2e-spec.ts`.

## Review round 2 fixes

- The sweep now runs before the role matrix, because the matrix's owner rows delete the single spare rows and a later intruder DELETE hit an id that no longer existed (a cross-tenant delete mutant survived). Proof: mutant "delete by id when the table is another restaurant's, still answer 404" → `DELETE /api/tables/:spareTableId … nothing changes` fails; reverted.
