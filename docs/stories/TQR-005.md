# TQR-005: Staff accounts and role guard

- Release: v0.2.0 · Status: review · Owner: Claude (deliver-loop)
- Spec: S5 (AC14–AC16), design.md (Data: users, auth_sessions; API `/api/staff/*`), ADR 0002, ADR 0003, `docs/design-system.md`

## Story

As a restaurant owner, I want to give each person their own account with a role, so that the cashier, the waiters and the kitchen each see only their own screen — and so that I can lock someone out the moment they leave.

INVEST: Independent ☑ (after TQR-004) Negotiable ☑ Valuable ☑ Estimable ☑ Small ☑ Testable ☑

## Design

- API (`src/staff/`): `GET /api/staff` (max 200, oldest first), `POST /api/staff`, `GET /api/staff/:id`, `PATCH /api/staff/:id` `{displayName?, role?, active?}`, `PUT /api/staff/:id/password` `{password}` → 204. Controller-level `@UseGuards(StaffGuard) @Roles('owner')`; tenant from the session only; malformed id → 404. Pure rules in `domain/staff-rules.ts` (`staffChangeRefusal`, `endsSessions`). No schema change: `users.display_name`, `disabled_at` and `users_email_key` already exist.
- Identity: `pg-error.ts` shared unique-violation helpers; `identity.errors.ts` (codes + `emailTakenError`).
- Web: `/quan-ly/nhan-vien` (list → detail), `/quan-ly/nhan-vien/them`, `/quan-ly/nhan-vien/:id`; role homes `/thu-ngan`, `/phuc-vu`, `/bep` (placeholder "Màn hình này sắp có" in the new `StaffShell`). New shared `StatusChip` (icon + word); pages reuse main's `ConfirmSheet`, `RadioCardGroup`, `LoadingState`, `ErrorState`, `EmptyState`. Main's routes get `meta.roles`: settings and QR print owner-only, tables list owner/cashier/waiter, guest `/t/:qrToken` public. Router: `meta.roles` (omitted = owner only, deny by default), wrong role → own home, signed-in visitor of sign-in → own home; the API client calls an unauthorized handler on any 401 that sends the user to sign-in with `next`.

## Decisions

- New people get cashier/waiter/kitchen only; promotion to owner is a role change afterwards (spec lists those three for creation).
- Disabled sign-in keeps the generic `INVALID_CREDENTIALS` (no account enumeration).
- A new password ends the person's sessions as well as disabling does; a role change does not (the role is read on every request).
- The owner cannot reset their own password here (no current-password check); a self-service password change is a backlog item.

## Out of scope

- Real cashier/waiter/kitchen screens (TQR-014/015/019), password reset by email, audit log of staff changes.
