# TQR-014: Kitchen station queue — FIFO, skip with reason, late highlight

- Release: v0.4.0 · Status: done · Owner: Claude (parallel agent, kitchen worktree)
- Spec: S9 (AC30–AC34), AC31 realtime; design.md (Data: `order_items`), ADR 0003, ADR 0004, ADR 0005, `docs/design-system.md` (kitchen: 20 px+ text, 56 px targets)

## Story

As a cook, I want one queue per station ordered by arrival, so that earlier tables are served first — the product's core promise.

INVEST: Independent ☑ (items seeded straight into the database; ordering TQR-012 builds in parallel) Negotiable ☑ Valuable ☑ Estimable ☑ Small ☑ Testable ☑

## Non-functional

- Fairness fitness function (benchmarks/plan.md "Rush replay"): 30 tables, 302 items, 1 161 random cook/waiter actions → **0 out-of-order finishes without a recorded skip** (541 refusals, 286 reasons recorded). A mutation (skip rule disabled) makes the test fail.
- AC31 measured in e2e: done → station / floor / session delivery 5.2 / 5.2 / 4.9 ms (local Postgres; TQR-010 spike: 300 streams p95 21 ms).
- Accessibility: tickets are `article`s labelled by "Bàn 3 · 5 khách", buttons described by the ticket; station tabs follow the WAI-ARIA tabs pattern (arrow keys); axe serious/critical = 0 on the queue and the skip sheet (iPad).
- Kitchen sizing: body 20 px (`--font-size-kitchen`, new token), dish 24 px, buttons 56 px (`BaseButton size="lg"`).
- Clock skew: the queue carries `serverTime`; the iPad offsets its clock, so wait time and lateness are right on a device whose clock is off. The threshold is applied once on the server (`lateAt`).

## Design

- API (`src/kitchen/`): `GET /api/kitchen/stations` (with waiting/cooking counts), `GET /api/kitchen/stations/:id/queue` → `{station, serverTime, items: Ticket[]}`, `POST /api/kitchen/items/:id/start` `{version}`, `POST /api/kitchen/items/:id/done` `{version, skipReason?}` → `{id, status, version, skipReason}`; `GET /api/stream/station/:id` (snapshot = the queue). Roles `owner`, `kitchen`.
- Domain: `domain/queue.ts` — `compareQueueItems` on microsecond keys (Postgres precision; JS `Date` would tie items < 1 ms apart), `QUEUE_ORDER_COLUMNS`, `findSkippedOlder`; `domain/late.ts` (`lateAt`, `isLate`); `domain/item-status.ts` (transitions).
- Service: one transaction per action: `select … for update` → version check (→ `STALE_VERSION`) → transition check (→ `INVALID_TRANSITION`) → skip check (AC32) → `update … where status = ? and version = ?` → three `publish(tx, …)`.
- Web (`web/src/features/kitchen/`): `/bep` (roles kitchen, owner) — station tabs (`?khu=<id>` keeps the tab), `StationQueue` keyed per station with `useStationQueue` (snapshot, deltas by id + version via `queue-state.ts`, debounced re-read for unknown items, server-corrected clock), `TicketCard`, `SkipReasonSheet` (BaseSheet + TextAreaField; older tables taken from the local queue order).
- Decisions: separate start/done endpoints instead of `PATCH /api/items/:id/status` (role guard per route, cleaner matrix); `done` only from `cooking` (strict ADR 0005 §4 — two taps for a drink, accepted for honest wait data); skip reason stored only when it really was a skip; ADR 0005 names `item_id` and `service/domain/queue.ts` — the shared schema has `seq` and the lead placed the code in `kitchen/domain/` (no ADR change: same rule, tie-breaker is creation order).

## Review score

Independent review (code-reviewer agent, round 1): **9/10**, requirements fit 1, security 1 — approve. Fixed after review: the waiter board re-read on every floor delta (now only `done` / `served` / `cancelled`), and a slow older board read could briefly bring back a served dish (now only the newest read lands). Left as known limits: the ready-board query is unbounded per open session (fine at 30 tables), the client's seen-version map is not pruned within a shift, API problem `detail` strings are Vietnamese like the other contexts'.

**Final gate: 9.5/10 — PASS** (independent reviewer, 2026-11-08; per-criterion tables in docs/delivery/001-qr-table-ordering/status.md "Review scores").
