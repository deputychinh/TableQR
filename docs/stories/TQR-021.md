# TQR-021: Staff booking list — confirm, seat, cancel, late

- Release: v0.3.0 · Status: review · Owner: Claude (parallel agent, branch of main 24b16cf)
- Spec: S15 (AC51–AC53), AC3 (isolation), AC15 (roles), design.md (Data: bookings, table_sessions), ADR 0003, ADR 0004, ADR 0007, `docs/security.md` (30-day retention)

## Story

As staff (owner, cashier, waiter), I want one list of the day's bookings where I confirm, seat or cancel them, so that booked guests get their table and late ones are visible.

INVEST: Independent ☐ (after TQR-020, same branch) Negotiable ☑ Valuable ☑ Estimable ☑ Small ☑ Testable ☑

## Decisions (recorded)

- **Retention job**: a plain hourly `setInterval` in `RetentionJob` (started on bootstrap, `unref`ed, cleared on shutdown) instead of `@nestjs/schedule` — one idempotent `UPDATE` needs no cron library and is harmless when every API process runs it. `BookingService.purgeExpiredPersonalData(now)` and `RetentionJob.run()` are called directly by the tests. It is a system job across all restaurants (no tenant), by design.
- **Seat** is allowed from `pending` (walk-in before anyone confirmed) and from `confirmed`; the session insert and the status change are one transaction, so a busy table leaves the booking untouched.
- **Confirm again** on a confirmed booking = move it to another table.
- **Shell**: owner → `OwnerShell` (new nav item "Đặt bàn"); cashier / waiter → `StaffShell`, reached from a "Đặt bàn" link on their placeholder homes until TQR-015/019 build those screens.
- The owner sees the public link `/r/<slug>/dat-ban` with a copy button.
- Realtime: every action publishes `booking.status {bookingId, status, version, tableId, sessionId}` on `floor` inside its transaction; the page refreshes on that delta and on every snapshot.

## Design

- API (owner, cashier, waiter): `GET /api/bookings?date=` (today in Vietnam by default) → `{date, items}`; `POST /api/bookings/:id/{confirm,seat,cancel,no-show}` (`confirm` body `{tableId?}`) → the updated booking view. Each action locks the row (`FOR UPDATE OF bookings`), checks the move in `nextStatus`, bumps `version`.
- Web: `features/booking/pages/BookingsPage.vue` (day stepper + date picker, status chips, "Trễ", tap-to-call phone, notes, erased-data line, `TableChoiceSheet` for confirm/move with only fitting tables, `ConfirmSheet` for seat / cancel / no-show), `BookingCard.vue`.

## Known limits / follow-ups

- Deleting a table cascades to its bookings (same as sessions); TablesService should refuse a table with future bookings — left for the tables owner.
- With six owner sections the phone bottom bar wraps some labels onto two lines.
