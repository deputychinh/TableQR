# TQR-015: Waiter ready list and serve

- Release: v0.4.0 · Status: review · Owner: Claude (parallel agent, kitchen worktree)
- Spec: S10 (AC35–AC37), AC31 (waiter screen within 2 s); ADR 0003, ADR 0004, ADR 0005 §4, `docs/design-system.md`

## Story

As a waiter, I want a ready list by table, so that the right dishes reach the right table.

## Acceptance criteria (spec ids)

| Id             | Given                                           | When                              | Then                                                                                                              |
| -------------- | ----------------------------------------------- | --------------------------------- | ----------------------------------------------------------------------------------------------------------------- |
| AC35           | items marked "Xong" at several open tables      | the waiter opens `/phuc-vu`       | ready dishes are listed under their table, the table whose dish has been ready longest first, dishes oldest first |
| AC36           | a ready dish                                    | the waiter taps "Đã ra bàn"       | `served`, `served_by` = the waiter, `served_at` = now; it leaves the list at once; a second tap → 409             |
| AC37           | every non-cancelled item of a session is served | the board is shown                | the table shows "Đủ món" (icon + word); a table with dishes still in the kitchen shows "Còn N món"                |
| AC31 (waiter)  | the waiter's screen is open                     | the cook marks a dish "Xong"      | it appears without reload (floor stream delta → re-read of the board)                                             |
| T1 (roles)     | a kitchen user                                  | calls the ready list or serve     | 403; owner, cashier and waiter may serve (cashiers run dishes in small shops)                                     |
| T2 (isolation) | restaurant B's waiter                           | serves A's item / reads the board | 404 / only B's tables                                                                                             |

## Design

- API: `GET /api/serve/ready` → `{tables: [{sessionId, tableName, partySize, ready[], remaining, served, complete}]}` (open sessions, cancelled items ignored; `domain/ready-board.ts`), `POST /api/serve/items/:id/serve` `{version}` (compare-and-set `done → served`, publishes `item.status` to station, floor, session).
- Floor stream snapshot: `src/realtime/floor-snapshot.ts` `FloorSnapshotRegistry` — modules register a part under a key; snapshot = `{ at, ready, …}`. Held orders (TQR-013) or bills can register their own part without touching the stream controller.
- Web (`web/src/features/serving/`): `/phuc-vu` (roles waiter, cashier, owner) — `useReadyBoard` (floor stream `ready` snapshot, `applyReadyDelta` removes served dishes at once, debounced re-read for anything a delta cannot describe), `ReadyTableCard` (56 px "Đã ra bàn"), "Các bàn đang phục vụ" chips (`StatusChip`: "Đủ món" success / "Còn N món"), link "Đơn chờ duyệt" → `/phuc-vu/duyet` (screen built by TQR-013).

## Review score

Independent review (code-reviewer agent, round 1): **9/10**, requirements fit 1, security 1 — approve. Fixed after review: the waiter board re-read on every floor delta (now only `done` / `served` / `cancelled`), and a slow older board read could briefly bring back a served dish (now only the newest read lands). Left as known limits: the ready-board query is unbounded per open session (fine at 30 tables), the client's seen-version map is not pruned within a shift, API problem `detail` strings are Vietnamese like the other contexts'.
