# TQR-023: Step-up authentication for bank account changes

- Release: unreleased (after v0.5.0) · Status: review · Owner: Claude (parallel agent, branch of main e2007c8)
- Spec: S4 (house rules and bank account, TQR-008), AC4 (sign-in throttle), `docs/security.md` (Tampering: someone edits the bank account to theirs), OWASP ASVS 5.0 V6.3 / V7.5 (re-authentication before sensitive changes)

## Story

As a restaurant owner, I want the app to ask for my password before the account guests pay into is changed or removed, so that someone using my unlocked iPad or a stolen session cannot redirect the restaurant's money.

INVEST: Independent ☑ Negotiable ☑ Valuable ☑ Estimable ☑ Small ☑ Testable ☑

## Acceptance criteria

| Id  | Given                                                          | When                                                                                       | Then                                                                                                                                                                     |
| --- | -------------------------------------------------------------- | ------------------------------------------------------------------------------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| R1  | an owner session                                               | `PUT /api/restaurant/settings` with a new or removed bank account and no `currentPassword` | 422 `REAUTH_REQUIRED` (`fields: [{path: 'currentPassword', code: 'required'}]`); nothing changes                                                                         |
| R2  | the same                                                       | with a wrong `currentPassword`                                                             | 403 `REAUTH_FAILED`; nothing changes; the attempt is a failed sign-in of that email (`login_attempts`); the session stays valid                                          |
| R3  | the same                                                       | with the right `currentPassword`                                                           | 200; the account is saved; the attempt is recorded as a success                                                                                                          |
| R4  | rules change only, or the same account sent again              | saved without `currentPassword`                                                            | 200; no password check runs                                                                                                                                              |
| R5  | 10 failed checks (step-up or sign-in) in 15 minutes            | another step-up or sign-in, even with the right password                                   | 429 `LOGIN_BLOCKED`; after the window the right password works again                                                                                                     |
| R6  | a bank change                                                  | it is saved                                                                                | the `bank_account_changed` audit line holds who, when and the last 3 digits only; no log line holds the password                                                         |
| W1  | the owner changes or removes the account on `/quan-ly/cai-dat` | they save                                                                                  | the confirm sheet asks "Mật khẩu đăng nhập của bạn" (password field, `autocomplete="current-password"`, focused); empty → "Nhập mật khẩu để xác nhận." without a request |
| W2  | the sheet                                                      | the server answers `REAUTH_FAILED` / `LOGIN_BLOCKED` / `REAUTH_REQUIRED`                   | the reason shows under the field, the sheet stays open, the field is emptied and focused, the changes stay unsaved                                                       |
| W3  | the sheet                                                      | it is cancelled or the save succeeds                                                       | the typed password is gone (only a component `ref`, never a store or browser storage)                                                                                    |

## Decisions (recorded)

- **Same throttle as sign-in.** `AuthService.reauthenticate(userId, password)` reserves an attempt for the user's email under the per-email advisory lock (`reserveAttempt`, D1) before the scrypt check, and uses `checkCredentials` (one scrypt, `verifyPasswordLimited`). So step-up failures and sign-in failures share one budget of 10 per 15 minutes; a stolen session cannot be used to guess the password faster than the sign-in form allows.
- **Status codes**: wrong password → 403 (the session is valid, the action is refused; 401 would make the web client sign the owner out). Missing password → 422 `REAUTH_REQUIRED` with the field, so a client can show the field; an empty string is a plain `VALIDATION_FAILED` and costs no attempt. Throttled → 429 `LOGIN_BLOCKED`, the sign-in code.
- **Check outside the transaction.** The service compares the sent account with the stored one, verifies the password (≈100 ms of scrypt) _before_ opening the transaction, so no restaurant row lock is held during it; inside the locked transaction an account change without a verified password is refused (covers a concurrent change between the read and the lock).
- **Only when the account really changes** (`sameBank`): re-sending the stored account with a rules change needs no password, like the web page, which only opens the sheet when the account differs.
- **Web**: the password field lives in the existing bank `ConfirmSheet` (design system §3: confirm money actions with the consequence shown), built from `FormField` (type password, show/hide button, hint, inline error). `ConfirmSheet` now focuses the first form field when its body has one (else the first button) and keeps form fields inside its Tab trap — this also improves the staff "new password" and cashier "close reason" sheets. Enter in the field confirms.
- **Logs**: no request bodies are logged; the redaction pattern already covers `currentPassword` (`password` anywhere in the key); the audit line is unchanged.

## Known limits / follow-ups

- A successful step-up does not reset earlier failures (same as sign-in); the window expires them.
- An owner who forgot the password cannot change the account (there is no self-service password reset yet).
