# TQR-025: Re-sync the open bill when the kitchen cancels an item

- Release: unreleased (after v0.5.0) · Status: done · Owner: Claude (known issue of release 1)
- Spec: S12 AC40/AC42 (open bill follows what is due), S9 (kitchen), AC38 (guest sees "Đã huỷ"); ADR 0004 (events in the transaction), ADR 0005 (item compare-and-set)

## Story

As a guest with the bill open on my phone, I want the amount and QR to change at once when the kitchen cannot make one of my dishes, so that I never transfer money for food I did not get.

INVEST: Independent ☑ Negotiable ☑ Valuable ☑ Estimable ☑ Small ☑ Testable ☑

## Finding first

The existing cancel paths were searched in `src/kitchen` and `src/service`: the kitchen had **no** cancel action (only start → done → serve), a waiter rejecting a held order cancels items that were never billable (held orders are not billed, AC40a), and closing a session already supersedes the open bill. So the "kitchen cancel" of the known issue did not exist yet; this item adds it ("Bỏ món") with the bill re-sync inside it. Decision recorded here (decide-and-record).

## Non-functional

- Locks: the item row (compare-and-set), then the session row like bill requests and payments, so the one-open-bill-per-session index is never raced; a closed session is not re-synced (closing already superseded its bill).
- Realtime: events are published inside the transaction (ADR 0004); the guest bill page already reacts to `bill.status`.

## Design

- Domain `kitchen/domain/item-status.ts`: `cancel` from `waiting` or `cooking` to `cancelled`.
- `KitchenService.cancel` uses the shared `transition` with an `after` hook that locks the session and calls `syncOpenBill(tx, tenant, sessionId, now, {issueWhenNone: false})`.
- `POST /api/kitchen/items/:id/cancel` (owner, kitchen); role-matrix row added.
- Web: `TicketCard` "Bỏ món" (ghost, danger colour, 56 px), `StationQueue` `ConfirmSheet`, `cancelItem` service, locale `kitchen.drop.*`. "Bỏ món" rather than "Huỷ món" so the sheet's cancel button can stay "Huỷ" (design system).

## Review round 1 fixes

- **Nothing due after a drop.** With the bill superseded (or absent with something ordered) and `dueVnd = 0`, `GuestBill` shows the shared `EmptyState` "Bàn không còn món cần thanh toán" — "Món gọi thêm sẽ hiện ở đây cùng hoá đơn mới." — with a "Quay lại bàn" link to `/t/:qrToken`. Before, only `bill === null` showed an empty state, and the API keeps returning the superseded bill, so a reload showed the title alone. Both empty states ("Chưa có món…" and this one) now live in `GuestBill` (the page passes `tableUrl`), so live and reload render the same thing.
- **Copy no longer claims more food.** The change notice is neutral: "Hoá đơn đã thay đổi. Hãy quét mã mới bên dưới, đừng dùng mã cũ." (open bill) and "Hoá đơn đã thay đổi, đừng dùng mã cũ." (nothing due); the cashier's `BILL_SUPERSEDED` message lost "vì có thêm món" too.
- Tests, red before / green after: web `billing.test.ts` › TQR-025 with the bill superseded and nothing due it shows an empty state…, › the change notice does not claim more food…, › after a reload with the last dish dropped…, › live, the kitchen dropping the last dish… (6 failed before, 24/24 after); Playwright `e2e/billing.spec.ts` › TQR-025 live: the kitchen drops dishes while the guest has the bill open… (iPhone + iPad: owner on `/bep` drops "Trà đá" → new amount 110 000 ₫, new code and QR, neutral notice; drops "Bún chả" → empty state with the link, axe clean; reload → same; link → `/t/:qrToken`). Before the fix it failed on the copy, and with only the copy fixed it failed on the missing empty state.
