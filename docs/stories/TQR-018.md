# TQR-018: Bill with VietQR payload

- Release: v0.4.0 · Status: review · Owner: Claude (billing worktree)
- Spec: S12 (AC40–AC43), AC3; design.md (Data: `bills`), ADR 0003, ADR 0004, ADR 0006, `docs/security.md`, `docs/design-system.md`

## Story

As a guest, I want a bill with a VietQR code for the exact amount, so that I can pay by bank transfer from my table without waiting for the cashier.

INVEST: Independent ☑ (session/order tables from 0004 exist; fixtures stand in for TQR-011/012) Negotiable ☑ Valuable ☑ Estimable ☑ Small ☑ Testable ☑

## Design

- Data (`0005_billing`): `bills(restaurant_id, id, session_id, code, amount_vnd bigint, status open|superseded|paid, created_at, paid_at, paid_by, method)`; composite FK `(restaurant_id, session_id)` → `table_sessions`; `unique (restaurant_id, code)`; partial unique index one `open` bill per session; checks on amount range (1 … 13 digits), code alphabet, paid fields all-or-none.
- Domain (pure, unit-tested): `billing/domain/{crc16,vietqr,bill-code,totals}.ts`. `buildVietQr` writes `00=01, 01=12, 38={00=A000000727, 01={00=BIN, 01=account}, 02=QRIBFTTA}, 53=704, 54=amount, 58=VN, 62={08=memo}, 63=CRC`; `decodeVietQr` parses and checks the CRC. Bill codes use `crypto.randomInt` over the Crockford alphabet.
- Known-good vectors (reproduced byte for byte): liopay/vietqr README (`…62230819thanh toan don hang630470FA`, https://packagist.org/packages/liopay/vietqr) and vietqr_generator README (`…62160812henry an cut6304A322`, static 01=11, https://pub.dev/packages/vietqr_generator), plus the CRC catalogue check value `"123456789"` → `29B1`.
- Service: `requestBill` locks the session row (`for update`), computes due = billable total − paid bills, then `decideBill` (reuse / supersede + issue / supersede only). A code clash draws again (`on conflict (restaurant_id, code) do nothing`). `bill.status` is published to `session:<id>` and `floor` inside the transaction.
- API: guest `GET/POST /api/g/bill`, `GET /api/g/bill/stream` (SSE on `session:<id>`, snapshot = the bill view); staff `POST /api/bills {sessionId}` (owner, cashier, waiter), `GET /api/bills/:id` (owner, cashier), `GET /api/sessions/:id/bill` (owner, cashier, waiter).
- Web: `features/billing/components/GuestBill.vue` (amount large, QR via the shared `QrImage`, bank short name, holder, account, memo, "Mở app ngân hàng và quét mã", "Thanh toán tại quầy", change notice, "Đã thanh toán"), page `/t/:qrToken/hoa-don` (POST on open, live via the guest bill stream, no-session / closed / error states).

## Decisions

- The bill covers orders in `released` or `awaiting_payment`; `held` orders are not billed until accepted (a waiter may still reject them).
- After a payment, a further request bills only the remainder (total − paid), so pay-before-cooking can pay round by round.
- Guest stream lives under `/api/g/bill/stream` so this item does not depend on TQR-016's guest stream; it can be folded into `/api/g/stream` later.
- The guest cookie name `tqr_guest` and its lookup (`BillingService.guestContext`) are defined here; when TQR-011 lands a shared guest guard, billing should switch to it.
