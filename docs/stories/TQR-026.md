# TQR-026: `make bench` tolerant of per-IP limits

- Release: unreleased (after v0.5.0) · Status: done · Owner: Claude (known issue of release 1)
- Spec/design: spec "Quality targets" (order submit p95 ≤ 300 ms), `benchmarks/plan.md`, `docs/security.md` (per-address limits), TQR-003 (harness)

## Story

As the team, I want `make bench` to pass whenever the API is healthy, even right after other local traffic, so that a red bench means a slow API and not a rate limit hit during setup.

INVEST: Independent ☑ Negotiable ☑ Valuable ☑ Estimable ☑ Small ☑ Testable ☑

## Acceptance criteria

| Id            | Given                                                                     | When                       | Then                                                                                                                               |
| ------------- | ------------------------------------------------------------------------- | -------------------------- | ---------------------------------------------------------------------------------------------------------------------------------- |
| B1            | the sign-up limit (20/min per address) used up by a burst of sign-ups     | `make bench`               | setup waits with backoff, retries, and the run passes; stdout and `api.json` report `setup_429_retries` and `setup_429_wait_s`     |
| B2            | the check-in limit (30/min per address) used up                           | `make bench`               | same, on the check-in step                                                                                                         |
| B3            | a run just finished                                                       | `make bench` again at once | it passes                                                                                                                          |
| B4 (negative) | a limit that does not clear within `SETUP_RETRY_BUDGET_S` (default 150 s) | `make bench`               | setup stops with `<step>: still 429 after waiting N s`, no result is written (never a baseline)                                    |
| B5 (security) | production                                                                | —                          | no limit is changed or bypassed; the measured window (`POST /api/g/orders`) never retries, so a 429 there still counts as an error |

## Design

- `bench/api.js`: `withRetry(send, what)` around every setup POST (sign-up, menu, tables, check-ins): on 429 sleep 2, 4, 8, 16, 16… s within the budget, count with k6 `Counter`s `setup_429_retries` / `setup_429_wait_s`; `setupTimeout` = 60 s + budget.
- `benchmarks/plan.md`: why, how to raise limits for a bench-only API process (`TQR_AUTH_RATE_LIMIT_PER_MINUTE`, `TQR_GUEST_CHECKINS_PER_MINUTE`), and the proof runs.
- Chosen over a bench-only API process because `make bench` runs against whatever API is up (the dev API on 3310), and the retry needs nothing restarted; the env route is documented for those who want no wait.

## Review round 1 fixes

- The retry loop moved out of `bench/api.js` into the pure module `bench/lib/retry.mjs` (`backoffSeconds`, `createSetupRetry({budgetS, sleep, fail, onRetry, warn})`); k6 passes its `sleep`, `fail` and the two `Counter`s, node tests pass fakes. `.mjs` like `scripts/`, so node loads it as ESM without a `package.json` change; k6 imports it as is.
- `bench/lib/retry.test.mjs` (7 node tests) runs in `make test-scripts` (now `node --test scripts/ bench/`): the backoff sequence 2, 4, 8, 16, 16…, retry until a non-429, one counter entry per retry with its wait, no retry on other errors, the budget shared across calls and exhausted with `<step>: still 429 after waiting N s` (B4 is now tested, not "by construction"), and a non-throwing `fail` cannot loop. Red before: the module did not exist (`ERR_MODULE_NOT_FOUND`, 0 pass / 1 fail).
- Re-checked with k6 against a fresh API (port 3444) after 22 sign-ups: 6 retries on sign-up (2+4+8+16+16+16 = 62 s), `ok p95=15.83 ms`, so the counters still reach the summary.
