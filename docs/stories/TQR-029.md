# TQR-029: QR payment as a per-restaurant option (default off)

- Release: v0.6.0 · Status: done · Owner: Claude (deliver-loop)
- Spec: S4 (house rules, AC12), S12 (AC40, AC41 — reworded), S13 (AC44); owner ruling 2026-11-08 "các tính năng thanh toán thông qua qr code là option nhé"; ADR 0006 (VietQR), `docs/design-system.md`

## Story

As a restaurant owner, I want taking money by QR transfer to be something I switch on when I want it, so that I can run ordering and the kitchen from day one without giving a bank account — and my guests pay at the counter until I do.

INVEST: Independent ☑ (after TQR-018/019) Negotiable ☑ Valuable ☑ Estimable ☑ Small ☑ Testable ☑

## Decisions (decide-and-record)

- **Existing accounts keep QR on.** Data migration `0009_qr_payment_option` sets `payment.qrEnabled = true` where `bank_bin` is not null, so nobody silently loses QR on their bills; it does not move `rules_updated_at` (the restaurant's behaviour does not change, so it is not a new rules version). New restaurants default off.
- **QR availability reads the restaurant's current rules, not an order's snapshot.** It is how money is collected now, not a rule an order is judged by (AC12 snapshots stay for anomaly, approval and pay-before release). Turning QR off removes the QR from an already open bill at its next read.
- **Staff-recorded transfers stay possible in the API.** With QR off, `POST /api/bills/:id/pay {method:"transfer"}` is still accepted (a guest may transfer by hand, an older tab may still show the button); the cashier screen offers only "Đã nhận tiền", recorded as `cash`. Hiding is UX, not a security boundary — the money check is the cashier's either way.
- **Off keeps the saved account.** Switching off resets unsaved bank edits to the saved account and needs no password; switching back on uses it at once. Removal while off is an explicit "Xoá tài khoản đã lưu" (password step, TQR-023).
- **Pay before cooking stays** with QR off (cash at the counter); its copy never mentions QR.
- Cross-field rule (`on` needs an account) lives in `settings/domain/qr-payment.ts` and runs in the PUT schema (`superRefine`, path `bank`), so the 422 shape is the same as every other field error. The settings group `payment` is separate from other rule groups, so parallel rule additions merge cleanly.

## Non-functional

- Security: no VietQR payload and no account number in the bill response when off (asserted); step-up unchanged for account changes; tenant from the session/cookie as before.
- Accessibility: the switch is `role="switch"` with the label "Cho khách chuyển khoản bằng mã QR", described by its one-line explanation; the API's `bank` error lands on the bank select and focuses it; axe serious/critical = 0 on the counter bill, cashier screen and settings with the error.
- UX: one switch, one line of explanation, bank fields only when on; plain copy on the guest bill ("Mời bạn thanh toán tại quầy và đọc mã hoá đơn cho thu ngân.").

## Out of scope

- PayOS / SePay automatic confirmation (backlog); hiding a stored account from the owner's own settings view; per-table or per-hour QR rules.

## Design

- API: `houseRulesSchema.payment = { qrEnabled: boolean }` (strict), `DEFAULT_RULES.payment.qrEnabled = false`, old rows read with the default via `readStoredRules`; `qrPaymentNeedsBank` / `qrPaymentActive` (pure); `SettingsService.staffRules` and `BillingService.overview` add `qrEnabled`; `BillingService.buildView` only builds a VietQR when `qrPaymentActive(rules, bankStored)`.
- Data: migration `0009_qr_payment_option` (data only, no schema change).
- Web: `SettingsPage` section "Chuyển khoản (tuỳ chọn)" with `ToggleSwitch` and `BankAccountSection` inside; `model.checkDraft` skips hidden bank fields when off and asks for an account when on; `fieldOfPath('bank') → 'bank.bin'`; `CashierPage`/`CashierSessionCard` use `overview.qrEnabled`; copy in the locale files.
