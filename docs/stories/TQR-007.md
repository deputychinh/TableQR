# TQR-007: Tables, QR tokens, printable QR sheet, rotation

- Release: v0.2.0 · Status: review · Owner: Claude (deliver-loop)
- Spec: S3 (AC8–AC11), AC3 (isolation); design.md (Data: `dining_tables`), ADR 0002, ADR 0003, ADR 0006 (QR rendered client-side), `docs/design-system.md`

## Story

As a restaurant owner, I want to add my tables and print a QR code for each, so that every table identifies itself when a guest scans it — and I want to replace a code that was photographed or lost, so that the old one stops working.

INVEST: Independent ☑ (after TQR-004) Negotiable ☑ Valuable ☑ Estimable ☑ Small ☑ Testable ☑

## Non-functional

- Security: token = 16 bytes from `crypto.randomBytes` (128 bits), base64url, unique index; tokens never logged (route pattern only, tested); `Cache-Control: no-store` on table and guest reads so a rotation applies at once; tenant only from the session (ADR 0003); composite FK `(restaurant_id, table_id)` on retired tokens; malformed ids/tokens answer 404 without touching Postgres types; non-GET requests pass the Origin guard.
- QR: rendered in the browser with `qrcode` as SVG (no third-party image API), error correction M, 4-module quiet zone, black on white in both themes; a unit test decodes the matrix with `jsqr` back to the exact URL.
- Accessibility: every QR image has a name ("Mã QR của Bàn 1"); action buttons name their table ("Đổi mã QR của Bàn 1") and contain their visible label; sheets are native `<dialog>` (focus trap, Esc); axe serious/critical = 0 on every page of the journey.
- UX (owner rule): one primary action per screen ("Thêm bàn"), seats chosen with large −/+ buttons, destructive and code-changing actions confirmed in a sheet that spells out the consequence, polite status line after each action.

## Out of scope

- Ordering on the guest page (TQR-011/012), table sessions (TQR-010), bulk add, table areas/zones, rate limiting of the public guest endpoint (with the guest ordering items).

## Design

- API (owner writes, owner/cashier/waiter reads): `GET /api/tables` → `{items}` (max 200, oldest first), `GET /api/tables/:id`, `POST /api/tables` {name, seats} → 201, `PATCH /api/tables/:id` {name?, seats?}, `DELETE /api/tables/:id` → 204, `POST /api/tables/:id/rotate-qr` → 200 with the new token. Public: `GET /api/g/t/:qrToken` → 200 `{restaurant:{name,slug}, table:{id,name,seats}}` / 410 `QR_EXPIRED` / 404 `TABLE_NOT_FOUND`. Cap of 200 tables per restaurant → 409 `TABLE_LIMIT_REACHED` (creation serialised per restaurant with `SELECT … FOR UPDATE` on the restaurant row).
- Data (migration `0001_tables`): `dining_tables(id, restaurant_id → restaurants, name, seats check 1–30, qr_token unique, qr_rotated_at, created_at)` with `unique (restaurant_id, id)` for composite FKs and `unique (restaurant_id, lower(name))`; `retired_qr_tokens(qr_token pk, restaurant_id, table_id, retired_at)` → `(restaurant_id, table_id)` on delete cascade. Rotation = one transaction: lock the row, insert the old token into `retired_qr_tokens`, set the new token.
- Code: `services/api/src/tables/{tables.module,tables.controller,tables.service,tables.schema}.ts`, `domain/{qr-token,table-rules,table-error-code}.ts` (pure, unit-tested); names normalised to NFC, trimmed, spaces collapsed.
- Web: `web/src/features/tables/` — pages `TablesPage` (in `OwnerShell`), `TablePrintPage` (`/quan-ly/ban/in[?ban=<id>]`, no shell, `@page A4`, `break-inside: avoid`), `GuestTablePage` (`/t/:qrToken`, guest top bar); components `TableCard`, `TableFormSheet`, `QrImage`; `useTables` composable; `qr.ts` (URL builder, SVG data URL, natural sort). New shared, generic components in `web/src/components/`: `BaseSheet`, `ConfirmSheet`, `EmptyState`, `ErrorState`, `LoadingState`, `NumberStepper` (labels passed as props, so they carry no feature strings).

Found → fixed: the guest table chip (green on soft green) failed contrast (axe) → body text colour with a primary border; "In tất cả mã QR" wrapped to two lines on phones → toolbar stacks full width on compact; "Đổi mã QR" wrapped inside cards at 1180 px → cards min 24 rem (2 columns on iPad landscape) and no-wrap actions.

Review ruling D5 (2026-11-08): floor staff (waiter, cashier) may view and print table QR codes, because they replace a torn sticker during service. `/quan-ly/ban/in` is open to owner, cashier and waiter; `OwnerShell` builds its navigation from the router's `meta.roles` (`canOpen`), so a waiter sees their home ("Phục vụ") and "Bàn & QR" only; `StaffShell` shows a "Bàn & QR" link to roles that can open it. Tests: `OwnerShell.test.ts` (real route table and guard: owner sees five sections, waiter/cashier two; StaffShell link for waiter/cashier, none for kitchen); `tables.test.ts` › waiters see and print tables (now through the real guard — the earlier guard-less router hid the bounce); Playwright `e2e/floor-tables.spec.ts` (iPhone + iPad).

Decisions: tables are ordered by name naturally on the client (`Intl.Collator('vi', {numeric})`) — Postgres has no natural sort; names are unique case-insensitively (`lower(name)`) after NFC normalisation so "Bàn 1" typed on two devices is one name; a deleted table's codes answer "not found" (its retired tokens cascade away) rather than "expired", because the table no longer exists.
