# TQR-031: Client stream liveness — notice a silently dead stream and say so

- Release: unreleased · Status: review · Owner: Claude
- Spec: S9 (station queue), S17/S18 (kitchen voice), ADR 0004 (realtime), ADR 0010 (this change)

## Story

As a cook who listens rather than looks, I want the kitchen screen to notice when it stopped receiving orders and tell me — on screen and aloud — so that an outage never silently costs a table its order.

Found in review (2026-11-08): with the API down behind the Vite/nginx proxy, EventSource stays `readyState` 1 and no event arrives (the heartbeat was an SSE comment, invisible to EventSource); `useStream` stayed "live", the kitchen stopped showing and reading orders and nobody knew. A proxy 502 also made EventSource give up for good.

## Acceptance criteria

| Id  | Given                                                      | When                                                     | Then                                                                                                                                                            |
| --- | ---------------------------------------------------------- | -------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| L1  | an open stream                                             | the server's heartbeat comes due                         | it sends `event: heartbeat` `{intervalMs}` right after the first snapshot and every `TQR_SSE_HEARTBEAT_MS`                                                      |
| L2  | a live stream                                              | no event at all for 2.5 × the heartbeat (default 37.5 s) | the client closes it, status `reconnecting`, reopens after 1 s, then 2, 5, 10, 30 s…; a snapshot resets the backoff and sets `live`                             |
| L3  | a stream the browser gave up on (`readyState` 2), or `bye` | —                                                        | the client reopens it with the same backoff                                                                                                                     |
| L4  | the kitchen, waiter, guest order or guest bill screen      | the stream is `reconnecting`                             | a banner "Mất kết nối — đang kết nối lại…" (`role="status"`, icon + words + colour) until the next snapshot                                                     |
| L5  | "Đọc to" on                                                | the stream stays down 5 s                                | the voice says "Mất kết nối máy chủ" once, however long it stays down, and "Đã kết nối lại" once it is live; a shorter blip and the first connection are silent |
| L6  | the stream comes back                                      | the reconnect snapshot arrives                           | the queue is repaired from it; dishes already seen are not read again (TQR-027 dedupe kept); dishes released during the outage are read                         |

## Design

- API `realtime/sse.ts`: `beat()` writes the named event after the first snapshot and on every interval (the session check stays on the same timer).
- Web `composables/useStream.ts`: options `{create, heartbeatMs}`; a watchdog re-armed by every event (`open`, `snapshot`, `delta`, `heartbeat`, `resync`), interval taken from the server's `heartbeat`; `reconnectLater()` with `RECONNECT_DELAYS_MS`; listeners ignore a replaced EventSource.
- `components/StreamBanner.vue` (shared, in `docs/design-system.md`); kitchen `voice/useConnectionVoice.ts` (`LOST_GRACE_MS = 5 s`) wired in `StationQueue.vue`.
